# 织梦频道 · channel dream

《织梦频道》是一款以梦境探索、空间走位和卡牌放置为核心的邪典儿童玩具秀 roguelike。玩家进入的是一档会失控的节目；可构建房屋以纸盒、黏土和毛毡微缩布景呈现，不是写实住宅或传统恐怖山屋。Godot 4 客户端是当前唯一正式开发主线；Web 版只用于低成本验证玩法假设。Unity 工程不属于本仓库。

## AI 协作与需求落盘

本项目可以借鉴“先确认权威来源、按改动规模选择流程、结论必须落盘、修改必须可验收”的文档工作方法，但**当前仓库没有 OpenSpec、`GameDesign/`、`ai-workflow/setup-env`、Unity 或 Luban 管线**。不要照搬其他项目的 `/openspec-*` 命令、Change/Apply/Archive 流程，也不要为了小改动额外制造审批文档。

### 权威来源

1. 已拍板的产品和玩法结论以[现行主策划](./docs/design/织梦频道_channel_dream_策划案与招标书.md)为准。
2. 尚未决定或存在冲突的问题写入[未决设计](./docs/open-questions.md)，不得由 AI 根据 Web、竞品或聊天上下文自行拍板。
3. Godot 当前行为以 `godot/` 源码、数据和可执行回归测试为准；Web 只提供玩法历史参考。
4. 聊天记录、临时提示词、第三方截图和本机文件都只是输入。只有进入正式文档、数据、源码或测试后，才成为项目事实。

### 按任务规模选择做法

| 任务类型 | 项目内做法 |
| --- | --- |
| 只讨论想法、目标尚不明确 | 阅读现行设计与实现，整理目标、非目标、流程、风险和待决定项；用户未要求实现时不改源码 |
| 错别字、链接、已确认的小段说明 | 直接修改对应权威文档，检查链接和 diff，不创建额外方案文档 |
| 已确认的代码、UI 或资产调整 | 直接在 Godot 主线实施，补测试和实机截图；同步更新受影响的客户端事实文档 |
| 改变玩法规则、存档、配置结构或 1/3/5 格房间契约 | 先核对主策划和未决设计；把范围、兼容与验收写入对应设计/计划，再同时实施代码与回归测试 |
| 只要求诊断或审美评估 | 先提供有截图、代码或数据证据的结论；除非用户同时要求修改，否则不扩展成实现任务 |

用户明确要求“执行”“修改”“继续”时，默认直接执行当前已确认范围，不重复输出可行性确认或要求用户再次批准。只有缺少的选择会实质改变玩法、造成不可逆外部影响或扩大任务范围时才停下询问。

### 需求写清到可制作、可验收

新增功能或大改至少要在相关设计、计划或任务说明中明确：

- 玩家为什么需要它，本次目标与明确不做什么；
- 玩家从哪里进入、如何操作、成功/失败后到哪里；
- 正常、空数据、无效输入、中断与恢复状态；
- 涉及的数据文件、字段、默认值、非法值和旧存档兼容；
- UI 的信息层级、交互状态、分辨率适配及项目自有视觉输入；
- 可逐步执行的验收条件和应补的自动化测试。

视觉参考必须注明“参考什么、不参考什么”。第三方截图只能说明方向；涉及新页面、房间或明显布局变化时，要在项目内保留概念图、白模、地编模板或实机截图。美术验收不能只看资产是否加载，必须检查完整游戏画面中的比例、构图、遮挡、材质、光照、信息层级和操作状态。

### AI 执行顺序

1. 阅读本 README、[文档地图](./docs/README.md)和任务直接相关的设计/客户端 README。
2. 检查当前 Git 状态、正式 Godot 入口、相关数据和既有测试；不得根据旧聊天假设当前实现。
3. 明确本次会修改与不会修改的范围，优先复用现有场景、资产、编辑工具和测试。
4. 实施最小完整改动。Godot 是正式主线，不为了“同步”而顺手修改 Web。
5. 先跑定向测试，再按风险跑相关回归；视觉改动必须用 Vulkan 实机截图检查，不能只以 headless PASS 代替。
6. 把新的正式事实更新到对应 README/设计/数据；一次性分析和截图不冒充权威需求。
7. `git diff --check` 后只暂存本次明确修改的文件，提交并推送；不要带入 `.godot/`、`.import`、日志、截图、本机 MCP 配置、测试生成的 `user://` 数据或无关脏文件。
8. 交付时列明结果、修改文件、验证项、提交号，以及仍然存在但未包含在本次范围内的问题。

## 快速运行

### Web

```powershell
Set-Location "<repo>\web"   # <repo> = 本机 clone 出的仓库根
python -m http.server 8787
```

浏览器打开 `http://127.0.0.1:8787/`。桌面包与完整操作见 [Web README](./web/README.md)。注意：**Web 版以共享盘 `\\192.168.1.21\bytedance\Shared\new channel\web` 下 `CabinSlice_织梦频道.exe` 的实际行为为准**，本仓库 `web/` 已与该基准同步。

### Godot

技术要求：**Godot 4.7.x**（4.6 及更早版本不受支持）。打开 [godot/project.godot](./godot/project.godot)，或运行：

```powershell
<godot> --path "<repo>\godot" --editor
# <godot> = 本机 Godot 4.7.1 可执行文件；<repo> = 本机 clone 出的仓库根
```

- 主场景是 `godot/channel_3d.tscn`（`run/main_scene` 已指向它），编辑器里按 **F5** 运行；`godot/main.tscn` 是旧版 2D 原型，仅供历史对照，不要在其上开发。
- **不要**运行仓库外层目录里的 `DreamChannel.exe`——那是 2025 年的 Unity 旧构建，与本仓库无关。
- Godot 开发以各自本机仓库为准，不再依赖网络共享；首次资源导入后由 `.godot/` 缓存加速。详细技术要求与自检见 [Godot README](./godot/README.md)。

## 当前战斗状态（2026-08-24）

- 战斗规则已支持任意数量 `N` 个敌人：敌人拥有稳定 `enemy_id`，独立维护生命、韧性、视野、埋伏、致盲、记忆位置和行动状态；敌方回合按内容顺序逐个行动。
- 旧房间格式 `room.enemy + arena.enemy` 仍然兼容；正式快照目前仍以单敌人为主，多敌人房间使用 `room.enemies[]` 配置，尚未大规模写入正式内容。
- 当前敌人 AI 仍是确定性的优先级规则状态机，不是行为树、规划器或学习型 AI；本轮已加入回合级战术黑板和基础闭环。敌人会根据配置或特性自动分为 `hunter`、`flanker`、`controller`，每个敌方阶段重新感知、预订互不重叠的攻击位、执行移动/攻击，并在下一阶段重新规划；HUD 意图预览与实际行动共用这套计划。
- 现阶段仍未实现集火、保护、撤退、动态编队、诱导玩家走位和跨回合战术记忆；这些属于下一阶段。正式快照目前仍以单敌人为主，多敌人房间使用 `room.enemies[]` 配置。多敌人基础计划见 [.omc/plans/multi-enemy-refactor-plan.md](./.omc/plans/multi-enemy-refactor-plan.md)。
- 主菜单现有“后台测试 → 战斗与 AI 测试”已升级为隔离测试台：提供固定 Seed 的房间预设、手动战斗、AI 单步/连续观察、敌人角色与攻击位调试信息；测试不会结算正式奖励、推进集数或改写正式存档。详细执行计划见 [.omc/plans/combat-ai-test-mode-plan.md](./.omc/plans/combat-ai-test-mode-plan.md)。

## Godot 战斗测试与操作说明

战斗测试入口位于主菜单的“后台测试 → 战斗与 AI 测试”。这是隔离的开发测试场景，不会推进正式集数、结算正式奖励，也不会改写正式存档。测试台用于确认房间内战斗、敌人意图、敌方回合节奏、多敌人轮流行动和动画表现。

### 当前操作方式

- 玩家在棋盘上直接点击可到达的格子，系统会自动计算路径并连续移动；不再要求“选择节点 → 再确认移动”。
- 战斗中的方向按钮和 WASD/方向键仍然保留，适合快速验证单格移动；普通验收优先使用点击目标格的完整寻路流程。
- 点击“回合结束”后，敌人按行动顺序逐个执行移动、攻击或等待；敌方回合期间玩家输入会锁定，动画完成后才重新进入玩家回合。
- 战斗 HUD 会显示敌我行动顺序、当前行动者、敌人意图和可移动目标。多敌人场景中每个敌人拥有稳定的 `enemy_id`，不会因为节点重建改变身份。

### 战斗表现层结构

战斗场景将逻辑状态、棋盘表现和角色表现分开管理：

```text
CombatRules（权威战斗状态）
        ├── BattleBoard（格子、地形、意图、房间装饰）
        └── BattleActors（玩家、敌人、诱饵及角色动画）
```

- `build_battle_world()`：完整同步棋盘和角色，适用于进入战斗、玩家行动结算和动画全部结束后的最终状态同步。
- `refresh_battle_board()`：只刷新棋盘、地形和意图标记，保留角色节点实例；敌方回合动画期间只能使用这一类刷新。
- 敌方规则可以先计算出整回合事件，但角色表现按事件顺序播放。一个敌人一回合可以产生多条移动事件，动画初始化只使用第一条移动事件的 `from` 起点，不能被后续步骤覆盖。
- 敌人移动完成后才由完整同步把角色放到权威终点，避免出现“终点闪现一帧 → 回到起点 → 开始行走”的视觉跳变。

### 字体与跨平台显示

项目不依赖 Windows 或 macOS 的系统字体。中文界面当前使用项目内置的思源黑体：

- `godot/assets/fonts/SourceHanSansCN-Regular.otf`：普通界面、说明文字和默认主题字体。
- `godot/assets/fonts/SourceHanSansCN-Medium.otf`：按钮和强调文字字体。
- `godot/assets/fonts/app_theme.tres` 已指向项目内置 Regular 字体；HUD 代码直接引用项目内置 Regular/Medium 字体。

黄色背景按钮不绘制黑色文字偏移阴影，也不绘制额外的黑色底板；深色、青色和洋红色按钮仍可保留文字阴影以维持层次。字体文件、按钮绘制规则和项目引用必须一起提交，避免跨平台互传后出现字体丢失或界面重影。

### 定向回归测试

在安装 Godot 4.7.x 的机器上，可以从仓库根目录执行以下定向测试：

```powershell
<godot> --headless --path godot --script res://tests/enemy_turn_animation_regression.gd
<godot> --headless --path godot --script res://tests/combat_input_regression.gd
<godot> --headless --path godot --script res://tests/multi_enemy_pathing_regression.gd
<godot> --headless --path godot --script res://tests/combat_test_observer_regression.gd
```

其中 `enemy_turn_animation_regression.gd` 包含连续多格移动的首帧起点检查；视觉相关问题仍需要在 Godot 实机运行测试台，通过实际画面确认字体、阴影、角色移动和镜头表现。
